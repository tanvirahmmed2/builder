# Data Creation Architecture: API, Database, and Frontend Flow

This document details the architectural standard for how table data is created, managed, and synchronized across the PostgreSQL database, Next.js backend APIs, and React frontend components. It uses the **Apps** ecosystem as the reference implementation.

---

## 1. High-Level Architecture Overview

The system follows a modern decoupled data flow where user interactions on the client trigger authenticated actions handled by Next.js App Router API routes, which mutate PostgreSQL tables and external media storage (Cloudinary).

## 2. Database Schema Design (PostgreSQL)

Data is normalized across primary entity tables and dependent child tables.

### 2.1 Primary Entity Table (`apps`)
Located in `postgresql/schema.psql`:

```sql
CREATE TABLE IF NOT EXISTS apps (
    id SERIAL PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    slug VARCHAR(255) UNIQUE NOT NULL,
    description TEXT,
    short_description VARCHAR(500),
    is_published BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_apps_slug ON apps(slug);
CREATE INDEX IF NOT EXISTS idx_apps_published ON apps(is_published);
```

**Key Schema Features**:
- `is_published`: Defaults to `FALSE`. New records are created as drafts so users can safely configure titles, descriptions, and media before making them visible.
- `slug`: Unique constraint; auto-generated from `title`. Never manually typed.
- `description`: Stores formatted HTML content generated by the Tiptap rich-text editor.

### 2.2 Dependent Media Table (`apps_images`)
```sql
CREATE TABLE IF NOT EXISTS apps_images (
    id SERIAL PRIMARY KEY,
    app_id INT NOT NULL REFERENCES apps(id) ON DELETE CASCADE,
    image VARCHAR(500) NOT NULL,    -- Stores Cloudinary public_id (e.g. 'apps/xy123')
    image_id VARCHAR(255),           -- Stores Cloudinary secret asset_id
    title VARCHAR(255),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_apps_images_app_id ON apps_images(app_id);
```

**Key Storage Rule**:
- We never store arbitrary public image URLs. We upload real files or attach Cloudinary assets, storing the Cloudinary `public_id` in `image` and `asset_id` in `image_id`.
- `ON DELETE CASCADE`: Deleting an app automatically removes its associated image records.

## 3. The API Layer (`src/app/api/developer/apps/route.js`)

All interactions flow through a unified REST/RPC-style route handler supporting `GET` and `POST` (with action dispatching).

### 3.1 Authentication & Role-Based Authorization
Every modifying request checks the caller's role using `isManagerOrAdmin`:

```javascript
const auth = await isManagerOrAdmin(req);
if (!auth.success) {
  return Response.json({ error: auth.message }, { status: 403 });
}
```

### 3.2 Automated Slug Generation via `slugify`
Slugs are not accepted from user input. They are created dynamically using `slugify`:

```javascript
import slugify from 'slugify';

async function generateUniqueAppSlug(title, excludeId = null) {
  const base = slugify(cleanTitle, {
    lower: true,
    strict: true,
    trim: true,
  }) || 'app';

  let candidate = base;
  let counter = 1;
  while (true) {
    const existing = await query(
      `SELECT id FROM apps WHERE slug = $1 ${excludeId ? 'AND id != $2' : ''} LIMIT 1`,
      params
    );
    if (existing.rows.length === 0) return candidate;
    counter += 1;
    candidate = `${base}-${counter}`;
  }
}
```

### 3.3 Media Handling & Direct URL Formatting
When files are uploaded:
1. Direct file buffers are read from `multipart/form-data`.
2. Cloudinary's upload SDK receives the file buffer stream.
3. Upon upload completion, the API inserts `public_id` into `apps_images.image` and `asset_id` into `apps_images.image_id`.
4. The database query computes the direct access URL in PostgreSQL:
   ```sql
   CASE 
     WHEN ai.image LIKE 'http://%' OR ai.image LIKE 'https://%' THEN ai.image 
     ELSE 'https://res.cloudinary.com/' || '${CLOUDINARY_NAME}' || '/image/upload/' || ai.image 
   END AS url
   ```
5. Frontend clients consume `img.url` directly, eliminating the need for client-side Cloudinary environment variables or JS mapping loops.

## 4. The Frontend Layer

### 4.1 Draft-First Auto-Creation Workflow
Instead of filling out a massive modal before persisting anything to the database:
1. **Creation**: Clicking **Create App** (or submitting `AppCreateForm`) immediately sends `action: 'create_draft'` to the API using `axios.post`.
2. **Draft Initialization**: PostgreSQL inserts an initial record with `is_published = false` and an auto-slugified URL.
3. **Form Opening**: The newly created record is immediately opened in `AppUpdateForm.jsx`.
4. **Enrichment**: The user uploads media, types rich content, and toggles `is_published` to `true` when ready.

### 4.2 Rich Text Editing with Tiptap Editor
For long text descriptions, `AppUpdateForm.jsx` integrates `TiptapEditor.jsx`:
- **Packages**: `@tiptap/react`, `@tiptap/starter-kit`, `@tiptap/extension-placeholder`, `@tiptap/extension-link`.
- **SSR Safe**: Configured with `immediatelyRender: false` to eliminate React 19 hydration mismatches.
- **Controls**: Headings (H2, H3, Paragraph), Bold, Italic, Strikethrough, Lists (Ordered/Bullet), Code Blocks, Quotes, Undo/Redo, and Clear Formatting.
- **Data Binding**: Emits clean HTML string to `formData.description`.

### 4.3 Clean Card Previews
On directory listing pages (`src/app/(developers)/developer/apps/page.jsx`), rich text descriptions are stripped of HTML tags for multi-line clamping (`line-clamp-3`):
```javascript
{(app.description ? app.description.replace(/<[^>]*>/g, ' ').replace(/\s+/g, ' ').trim() : '') || 'No detailed description provided yet.'}
```

### 4.4 Multi-Image Upload & Asset Library
1. **Direct Uploads**: Standard `<input type="file" multiple accept="image/*" />` feeds files into `FormData` and sends them via `axios.post` with `action: 'upload_images'`.
2. **Asset Library**: An integrated Cloudinary browser allows users to view assets already present in their Cloudinary cloud and attach them directly with `action: 'attach_cloudinary_asset'`.

## 5. Summary Blueprint for Adding New Tables / Modules

To replicate this pattern for new modules (e.g. `themes`, `packages`, `features`):

| Step | Layer | Implementation Rule |
|---|---|---|
| **1. Database** | PostgreSQL | Define table with `id`, auto timestamps, `is_published` (if draftable), and child media tables. |
| **2. Permissions** | API | Restrict mutations (`POST`, `PUT`, `DELETE`) to `admin` and `manager` roles; return `403` otherwise. |
| **3. Slugs** | API | Use `slugify(title, { lower: true, strict: true, trim: true })` + uniqueness resolution. Never take manual slugs from UI. |
| **4. Cloudinary** | API | Store `public_id` in `image` and `asset_id` in `image_id`. Return direct `url` field on image objects. |
| **5. HTTP Client** | Frontend | Always use `axios` for client requests (never `fetch`). |
| **6. Long Text** | Frontend | Use `<TiptapEditor />` for `description` or articles, and strip HTML tags on card excerpts. |
| **7. Creation** | Frontend | Implement a draft-first auto-creation flow (`Create Draft` -> edit in place -> `Publish`). |
